# ChatLogMidi - Chat Log Pruning and Popout Support

*Last updated: 2026-01-06*

## Overview

`ChatLogMidi` is a custom chat log class that extends `ChatLog5e` to provide DOM pruning functionality. This prevents performance degradation when many chat messages accumulate during a session.

This is now superseded by the separate Chatlog-prune module.

## Class Hierarchy

```
foundry.applications.sidebar.tabs.ChatLog  (Foundry core)
    └── ChatLog5e                          (dnd5e system)
            └── ChatLogMidi                (midi-qol)
```

- **ChatLog**: Foundry's base chat log implementation in Application v2 framework
- **ChatLog5e**: dnd5e's extension adding intersection observer for tray states and card visibility tracking
- **ChatLogMidi**: midi-qol's extension adding DOM pruning and per-instance message tracking

## Installation

ChatLogMidi is installed by replacing `CONFIG.ui.chat` during the `init` hook in `midi-qol.ts`:

```typescript
Hooks.once('init', async function () {
  if (game.settings.get("midi-qol", "pruneChatLog")) {
    BaseChatLogClass = CONFIG.ui.chat;  // Save original for reference
    CONFIG.ui.chat = ChatLogMidi;       // Replace with midi's implementation
  }
});
```

This causes Foundry to instantiate `ChatLogMidi` instead of `ChatLog5e` when creating the sidebar chat tab. The same class is used for both the main sidebar and any popped-out chat windows.

## Features

### DOM Pruning

When enabled via the "Prune Chat Log" setting, the chat log automatically removes old messages from the DOM when the count exceeds twice the configured batch size (`CONFIG.ChatMessage.batchSize`, default 25).

**How pruning works:**

1. `scrollBottom()` is called (e.g., when a new message arrives)
2. `pruneElement()` triggers a debounced call to `#doPrune()`
3. `#doPrune()` checks the DOM child count in `.chat-scroll .chat-log`
4. If count >= `batchSize * 2` (default 50), pruning begins
5. Loop removes oldest messages (first children) until count equals `batchSize`
6. For each removed message:
   - The message ID is removed from `#renderedIds`
   - For main sidebar only: `message.logged` is set to `false`
   - The element is removed from the DOM via `element.remove()`
   - `#lastId` is updated to track the oldest remaining message

### Batch Rendering

Messages are rendered in batches to improve performance:

- Initial render shows the most recent `batchSize` messages
- Scrolling up triggers `renderBatch()` to load older messages
- A semaphore prevents concurrent batch rendering

### Popout Support

The chat log can be popped out into a separate window. Both the main sidebar and popout maintain independent state:

- Each instance tracks its own rendered messages via `#renderedIds` Set
- Each instance prunes its own DOM independently
- Pruning or scrolling in one window does not affect the other

## Implementation Details

### Per-Instance State

Each `ChatLogMidi` instance maintains private state to track rendering independently:

| Property | Type | Purpose |
|----------|------|---------|
| `#renderedIds` | `Set<string>` | Message IDs currently rendered in this instance's DOM. Used to skip already-rendered messages. |
| `#lastId` | `string \| undefined` | ID of the oldest rendered message. Used by `renderBatch()` to determine where to start loading older messages when scrolling up. Note: This is distinct from Foundry's `ChatLog#lastId` - midi-qol maintains its own tracking. |
| `#renderingBatch` | `boolean` | Flag to prevent concurrent batch rendering. Set `true` at start, `false` at end of `#doRenderBatch()`. |
| `#renderingQueue` | `Semaphore` | Foundry utility to serialize batch render calls, ensuring only one batch renders at a time. |
| `#pruneDebounce` | `Function` | Debounced function (100ms) to batch pruning operations when many messages arrive quickly. |
| `#overflowingDebounce` | `Function` | Debounced function (100ms) to update `.overflowed` CSS class on scroll container. |

**Why per-instance state matters:**

The main sidebar and popout are separate `ChatLogMidi` instances with separate DOMs. Without per-instance tracking:
- Rendering a message in the main sidebar would mark it as rendered globally
- The popout would skip that message, appearing empty
- Pruning in one window would incorrectly affect the other's state

### Window Close/Reopen Handling

When a popout is closed, the `close()` method clears `#renderedIds` and `#lastId`. This ensures that if the same application instance is reused when reopening, messages will render fresh.

### Message Logged Flag

The `message.logged` property is a Foundry core concept. ChatLogMidi handles it as follows:

- **Main sidebar only**: Updates `message.logged = true` when rendering, `message.logged = false` when pruning
- **Popout**: Does not modify `message.logged` to avoid interfering with the main sidebar
- **Internal logic**: Uses `#renderedIds` for skip/render decisions, not `message.logged`

This separation ensures:
1. Core Foundry and other modules that depend on `message.logged` continue to work
2. Main sidebar and popout can render/prune independently

### Debounced Operations

Both pruning and overflow detection are debounced to batch rapid operations:

- `#pruneDebounce`: Batches pruning when many messages arrive quickly (100ms)
- `#overflowingDebounce`: Batches CSS class updates (100ms)

Elements are removed using `element.remove()`. Modern browsers handle garbage collection of detached DOM elements and their event listeners automatically.

## Design Decisions

### Why a Subclass Instead of Hooks or MutationObserver?

Simpler approaches were considered but rejected due to Foundry's internal state management:

**Approaches Considered:**

1. **Hook-based pruning** (`renderChatMessage` hook) - Prune old elements when new messages render
2. **MutationObserver** - Watch for DOM additions and prune when threshold exceeded

**Why These Don't Work:**

Foundry's `ChatLog` uses a private `#lastId` property to track the oldest rendered message. When the user scrolls up, `renderBatch()` uses this ID to determine where to start loading older messages:

```javascript
// Foundry's ChatLog.renderBatch() uses #lastId like this:
let lastIdx = messages.findIndex(m => m.id === this.#lastId);
// Then renders messages older than lastIdx
```

A hook or MutationObserver approach could successfully prune DOM elements, but:

- Cannot access Foundry's private `#lastId` (JavaScript private fields are truly private)
- Cannot update `#lastId` when pruning removes the oldest message
- Result: After pruning, `#lastId` points to a message no longer in DOM
- When user scrolls up, `renderBatch()` would load from the wrong position or fail entirely

**The Subclass Solution:**

By subclassing `ChatLog5e`, midi-qol can:

1. Maintain its own `#lastId` tracking that stays synchronized with pruning
2. Override `renderBatch()` to use midi's `#lastId` instead of Foundry's
3. Keep scroll-up functionality working correctly after pruning

## Configuration

Enable chat log pruning in midi-qol settings:

- Setting: "Prune Chat Log" (`pruneChatLog`)
- When enabled: `CONFIG.ui.chat` is set to `ChatLogMidi`
- Batch size: Controlled by `CONFIG.ChatMessage.batchSize` (default 25)
